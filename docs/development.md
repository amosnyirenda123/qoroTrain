# Development guide

## Repository layout

```text
.
├── src/qorotrain/          # the package (src layout)
│   ├── bridges/ cli/ config/ connectors/ messages/
│   └── routes/ runners/ store/ trackers/ tuners/
├── examples/               # bandits.ipynb + bandits.yaml; test_examples.py and test_e2e.py use them
├── tests/                  # pytest suite; helpers.py and nbhelpers.py are shared helpers
├── docs/                   # this site (Sphinx + MyST) and the generated YAML reference
├── pyproject.toml          # metadata, dependencies, console scripts, dependency groups
└── uv.lock                 # locked dependency versions (generated by uv; do not edit)
```

Generated or third-party content that is not project source: `.venv/`,
`uv.lock`, `docs/_build/`, `__pycache__/`, `.pytest_cache/`, and
`docs/experiment-yaml-reference.md`, which is generated (see below).

## Setting up

```bash
uv sync                    # runtime + dev dependencies into .venv
uv sync --group docs       # add the documentation toolchain
uv pip install ipykernel  # a python3 kernel; test_e2e.py skips without one
```

## Running the tests

```bash
uv run pytest -q                    # unit tests; broker tests skip themselves
docker compose up -d                # Mosquitto on localhost:1883
uv run pytest -q -m broker          # MQTT integration and end-to-end tests
```

- `test_mqtt_integration.py` needs a broker on `localhost:1883`.
- `test_e2e.py` also needs a `python3` Jupyter kernel that can import
  `qorotrain`.
- The `broker` marker is not registered in `pyproject.toml`, so pytest prints
  `PytestUnknownMarkWarning` for it.

Most tests run components for real on background threads, with
`helpers.FakeConnector` in place of a broker. `helpers.wait_for` polls a
condition instead of sleeping for a fixed time. `test_runner.py` replaces
Papermill with small Python scripts (`ScriptRunner`) to simulate exit codes,
signals and stubborn processes.

## Design rules to preserve

These invariants run through the code. A change that breaks one usually breaks
the architecture.

1. **Route handlers return quickly.** They run on the Bridge's single dispatch
   thread. Record data or hand work to your own thread. Never block on the
   network, a subprocess or a person there.
2. **Connector callbacks only enqueue.** They run on the broker client's
   network thread.
3. **One publisher per fact.** The Runner publishes run status and the Tracker
   publishes metrics. Do not add a second source of either.
4. **Topics and payloads go through `config.contracts.schema`.** Never format
   a topic string or a JSON payload elsewhere. Bump `SCHEMA_VERSION` for
   incompatible payload changes.
5. **Decode strictly and reject in one place.** Handlers catch `SchemaError`,
   log it and return.
6. **Tolerate redelivery.** QoS 1 means at least once. Every handler must be
   idempotent; see the table in [Architecture](architecture.md#topics-and-messages).
7. **Telemetry never breaks training.** The Tracker warns once and drops data.
   It does not raise.
8. **The schema is the source of truth for configuration.** See "Adding a
   configuration key" below.

## Adding a configuration key

1. Add the field to the relevant model in `src/qorotrain/config/models.py`
   (with `Field(...)` constraints). Unknown keys are rejected, so nothing reads
   a key the schema does not define.
2. Describe it in `DESCRIPTIONS` in `src/qorotrain/config/reference.py`. Use
   `RESERVED` if no code reads it yet, or `LABEL` if it only appears in
   messages.
3. Regenerate the reference page:

   ```bash
   uv run python -m qorotrain.config.reference > docs/experiment-yaml-reference.md
   ```

4. `tests/test_reference.py` checks that every key has a description, that the
   shown defaults are the real ones, and that the checked-in page is up to
   date. It also checks that `RESERVED` keys are not read: it fails if any
   source file other than `models.py` and `reference.py` contains one of the
   tokens `summarizer`, `use_notebook_context`, `retrieval`, `tuner.agent` or
   `.llm`. **This applies to comments and docstrings too.**

## Documentation conventions

### File header

Every first-party Python file (source, tests, `docs/conf.py`) starts with this
header. The header *is* the module docstring:

```python
"""
===============================================================================
Author: Amos Nyirenda
Date: 2026-11-07
Last Updated: 2026-11-07
File: qorotrain/package/module.py

Description:
    What the module does and why it exists, its responsibilities, how it
    interacts with other modules, and the design decisions behind it.

    Threading:
        Indented sections use the shared vocabulary listed below.

===============================================================================
"""
```

- `Date` is the date documentation was added. No historical creation date is
  recorded, because none is known reliably.
- Update `Last Updated` when you change a file.
- `File` is the path relative to `src/` (or the repository root for `tests/`
  and `docs/`), because several modules share a file name (`main.py`,
  `factory.py`, `__init__.py`).
- Do not add the header to generated files (`uv.lock`,
  `docs/experiment-yaml-reference.md`) or third-party code.

`docs/conf.py` contains an `autodoc-process-docstring` hook that turns the
banner into a field list and un-indents the Description, so the header renders
cleanly in the HTML.

### Docstrings

- **Google style**, parsed by Sphinx Napoleon: `Args:`, `Returns:`, `Raises:`,
  `Attributes:` (for classes and dataclasses), `Note:`, `Example:`.
- Document *why* and *what is guaranteed*: threading, idempotency, error
  behaviour and edge cases. Do not restate the code.
- Types go in annotations, not in `Args:` (autodoc copies the annotations into
  the parameter descriptions). In `Attributes:`, give the type in parentheses,
  because dataclass and Pydantic fields have no other place for it.
- Document module-level constants with a string literal on the line after the
  assignment (an attribute docstring).
- Extra section headers must be made only of letters and spaces, and must be
  registered in `napoleon_custom_sections` in `docs/conf.py`. The current
  vocabulary includes *Design*, *Threading*, *Concurrency*, *Side Effects*,
  *Error handling*, *Failure handling*, *Schema*, *Dependencies*,
  *Idempotency*, *Reliability*, *Backpressure*.
- Test functions do not need docstrings when their names already state the
  behaviour under test (for example `test_redelivered_batches_are_ignored`).

### Type annotations

Public functions and methods are fully annotated. Names that would create
import cycles are imported under `if TYPE_CHECKING:` and written as string
annotations (`"Bridge"`). The code must keep working on Python 3.12, where
annotations are evaluated when the function is defined, so every name used in
an unquoted annotation must be imported at runtime. Pydantic field annotations
and validator signatures are part of the schema's behaviour. Do not change
them for documentation purposes.

## Building the documentation

```bash
uv sync --group docs
uv run sphinx-build -b html docs docs/_build/html     # or: make -C docs html
uv run sphinx-build -W --keep-going -b html docs docs/_build/html   # warnings as errors
```

Open `docs/_build/html/index.html`. The site uses:

| Extension | Purpose |
|---|---|
| `myst_parser` | Markdown pages. ` ```mermaid ` fences become diagrams (`myst_fence_as_directive`), and they also render on GitHub. |
| `sphinx.ext.autodoc` | API pages from docstrings (`docs/reference/*.md`, one `automodule` per module). |
| `sphinx.ext.napoleon` | Google-style docstrings. |
| `sphinx.ext.viewcode` | "[source]" links to highlighted code. |
| `sphinx.ext.intersphinx` | Links to the Python standard library documentation. |
| `sphinxcontrib.mermaid` | Renders Mermaid diagrams in the browser. It loads mermaid.js from a CDN, so diagrams need network access. |
| `furo` | HTML theme. |

When you add a module, add an `automodule` entry for it to the matching page
in `docs/reference/`. `qorotrain.main` is deliberately not listed, because
importing it runs the CLI.

## Known gaps

These were found while documenting the code (2026-11-07). The documentation
describes the code as it is and points here where behaviour is incomplete.

### Packaging

- `pytest` is listed under runtime `dependencies` as well as in the `dev`
  group.
- The `langchain*`, `langgraph` and `pgvector` dependencies are not used by
  any module yet.
- The `qorotrain` console script is a placeholder that prints a greeting.

### Test suite

- No test drives `cli.main` in-process. The CLI is exercised only by the
  broker-gated `test_e2e.py`.
- The `broker` pytest marker is not registered.

### Not implemented (accepted by the schema)

- `tuner.algorithm: agent` and `optuna` (`AgenticTuner` and `OptunaTuner`
  raise `NotImplementedError`).
- `tuner.review.mode: manual`, the default. It is rejected unless a
  `Reviewer` is passed in code.
- The `tuner.summarizer` section and the agent's LLM section: validated,
  never read.
- The `alert` and `proposal` topics described in the README.
- RabbitMQ and Kafka connectors (configuration classes exist, connectors do
  not), and TLS for MQTT.

### Constraints worth knowing

- The Runner is POSIX-only (process groups and `os.killpg`).
- `application.name` becomes a topic level, but the schema does not reject
  `/`, `+` or `#` in it.
- `qorotrain.main` calls `sys.exit` when imported.

### README differences

`README.md` predates parts of the implementation. Where it differs, this site
and the code are correct:

- It says Python 3.10+, but `pyproject.toml` requires 3.12 or newer.
- It places the message schema at `messages/schema.py`. The schema is in
  `config/contracts/schema.py`.
- Its "Project structure" section is marked *proposed* and does not match the
  actual package names (for example `bridges/` and `tuners/`, not `bridge/`
  and `tuner/`).
